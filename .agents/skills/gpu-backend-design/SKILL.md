# 后端架构与接口设计

## 确定接口边界

1. 写清谁发起操作、输入包含哪些标识和限制、谁能看到结果。确认项目与实例等资源范围使用明确的输入或已有绑定。
2. 为读取和有副作用的请求分别定义成功语义。后台任务被接受后返回运行标识，并提供获取执行结果的方式。消费者能区分等待、成功、失败和结果待核对。
3. 将输入校验、登录会话和响应映射放在 HTTP 边界。将任务编排及外部写调用归 `worker`，让领域规则可用普通输入和测试替身单独运行。只抽取已有使用者需要的接口。
4. 标清 SQLite 的事务边界。列出必须一起提交的本地更新，以及事务结束后才发起的外部调用。记录两步之间进程退出时可用于恢复的状态，使用数据库唯一约束支撑跨进程去重。
5. 对外部响应按字段白名单建模。说明分页是否完整、数据采样时间、空值与错误时的表现。评估新旧客户端、已有数据和回滚时的兼容性。

涉及外部写入、幂等键、备份还原或任务重放时读取 [幂等与恢复评审规则](references/recovery-review.md)。

## 交付模板

| 设计项 | 需要给出的内容 |
| --- | --- |
| 接口与所有者 | 入口、消费者、同步或异步行为、输入与返回结果 |
| 持久状态 | 唯一键、合法转换、原子更新范围及迁移影响 |
| 失败与恢复 | 可重试错误、结果不明的处理、取消语义和对账证据 |
| 验收 | 一条正常路径、一条具有实际风险的失败路径，以及如何观察结果 |

规模很小的设计可合并为几个要点。对已存在的服务，以修改前调用方的行为作为兼容性基准。

## Gotchas

- 网络等待、通知投递与 SQLite 写事务分开。通知失败不应使云端动作重新提交。
- 单个 `worker` 的部署约定不能替代数据库约束或进程互斥。升级期间可能短暂出现两个进程。
- 备份恢复时，云端可能已经执行了备份之后的动作。列出恢复后核对的资源与时间范围。
